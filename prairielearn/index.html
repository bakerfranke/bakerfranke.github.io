01 What PrairieLearn is

PrairieLearn is an open-source, auto-gradable homework and exam platform — students answer coding, math, and interactive questions and get scored automatically wherever possible. UIC runs a hosted instance of it; CS 111 lives there as one course among many.

There are two separate repositories in play, and it matters which one you're in:

PrairieLearn/PrairieLearnplatform

The engine itself — the app that renders questions, runs the grader, serves the site. You will basically never need this repo.

PrairieLearn/pl-uic-cs111content

Our course's actual questions and assessments — plain files in a git repo. This is the one you'll clone and live in.

02 Get it running

Goal: clone the content repo, run a local copy of PrairieLearn against it in Docker, and confirm you can browse CS 111's questions. Fifteen minutes, no one else's help required.

  1. Clone the course repo

    Ask Baker for repo access first if you don't have it yet.

    git clone https://github.com/PrairieLearn/pl-uic-cs111.git

  2. Install Docker Desktop

    PrairieLearn ships as one Docker image — you don't build the platform from source. Grab it from docker.com/products/docker-desktop, install it, open it once, and wait for the whale icon to say it's running.

  3. Run PrairieLearn, pointed at the repo

    This mounts your local checkout into the container at /course. Swap in your actual path.

    docker run -it --rm -p 3000:3000 \
  -v ~/path/to/pl-uic-cs111:/course \
  prairielearn/prairielearn:us-prod-live

    The us-prod-live tag matches what's actually running our live course — closer to reality than the bleeding-edge default image.

  4. Load the course and look around

    Open localhost:3000/pl, click Load from disk in the top bar, and confirm CS 111: Program Design I shows up. Click into a question and hit Preview — you're now looking at a fully local, editable copy of the course.

Editing loop, once it's running

HTML / Python changes (question.html, server.py) — just reload the page in the browser.

JSON changes (info.json, infoAssessment.json) — click Load from disk first, then reload.

⚠ One thing this simple command can't do

Questions that auto-grade actual student-submitted code (not just a number or click) need "external grading" — PrairieLearn spins up a second, disposable Docker container per submission to run the code safely. The command above doesn't enable that. See §04 for what that means and which flags fix it — ask Baker if you hit a submission that just hangs.

04 Anatomy of a question

Every question folder has the same three core files. server.py always runs, but what it's responsible for depends on the grading method.

FileRole
info.jsonTitle, topic, UUID, and — critically — gradingMethod.
question.htmlMustache template. {{params.x}} is escaped, {{{params.x}}} drops in raw HTML built by server.py.
server.pygenerate() builds random params + the correct answer. grade() is optional, in-process scoring for value-type answers.

The three grading methods

MethodWhere code runsUse for
Internal Inside PrairieLearn's own server process — safe because the student only submits a value (a number, a click, a multiple-choice pick). Numeric answers, multiple choice, pl-drawing click-to-place questions.
External A second, disposable Docker container spun up per submission — the student's actual code gets executed there, isolated from the real server. "Write a function that…" coding questions. Needs an image, an entrypoint, and usually a tests/ folder in info.json.
Manual Nowhere — code is just saved. A human opens PrairieLearn's grading UI later and scores it by hand. Open-ended or design-y responses that can't be mechanically checked.

05 Getting a change live

The live site at us.prairielearn.com only ever reflects whatever is on this repo's master branch — and only after someone pulls it in. There's no way to preview a feature branch on the hosted site; that's what your local Docker copy is for.

  1. Branch, edit, push

    Work locally against Docker, same as §02, until it looks right.

  2. Open a PR, get it reviewed and merged to master

  3. Sync it on the live site

    An Editor/Owner goes to the course's Sync page and clicks Pull from remote git repository. Merging alone does not update the live course — this step is easy to forget.

There's also an in-browser file editor on the live site for quick one-off edits — it commits straight to master, bypassing review. Fine for typo fixes; use the git flow for anything that touches grading logic.

07 Karel autograding, start to finish

The short version, to repeat to a colleague building something similar: a Karel test file doesn't just pass/fail a submission — it can also report back exactly what the world and robot did, corner by corner and action by action. That one fact is the trick behind everything below: the same replay data renders an animated SVG for grading feedback, and the same test file's starting/ending world and expected robot state can drive the student-facing prompt itself, images included, with nothing hand-typed twice.

The three-layer architecture

LayerFileJob
Rendererkarel/pl_render.pyTurns a chronological (robot, action) event log into a self-contained animated SVG. Knows nothing about PrairieLearn or grading — portable to anywhere the karel library goes.
Adapterkarel/pl_adapter.pyBridges the karel library to PrairieLearn: runs a submission headlessly, exposes check_* functions (position, direction, beepers, world state, "was this method actually called," …), and writes results.json.
Spectests/karel_tester.pyThe only file that's actually different per question: the starting world, the expected ending state (or a model solution to derive it from), and which check_* calls matter for that problem.

Every question vendors its own full copy of karel/ under tests/karel/ — the external grading container only ever sees that question's own tests/ folder, so nothing can be shared by reference across questions. When you fix a bug in pl_adapter.py, copy it to every question's vendored copy by hand (or write a script — nobody has yet). The full function-by-function reference lives in tests/karel/README.md inside any of the questions below.

Authoring checklist — what you set vs. what's automatic

Every Karel question's tests/karel_tester.py answers the same handful of questions; everything else under karel/ is generic and never needs to change per-question.

You specify…As…Notes
Starting world (optional) STARTING_WORLD — embedded .kwld text, or a file loaded with read_world_file() Fed to world_setup_from_text(), then run_student(world_setup=...). Omit entirely for a blank, default-size world.
Expected ending state Either a model solution (MODEL_SOLUTION text/file, run once, then expected_robot_from_run() / expected_world_from_run()) — or a hand-typed EXPECTED_ROBOT dict / ENDING_WORLD text Prefer the model-solution route (baker_karel_delivery) — the expected answer can never quietly drift out of sync with the world or the solution. Hand-typing it (baker_karel_delivery_simple) is fine for a first draft or a very simple problem.
Starting robot Constructor args baked into STARTER_CODE's own UrRobot(street, avenue, direction, beepers) line, and/or a constructor_args tuple passed to check_solving_method_alone() / check_boolean_method() for isolated-method questions There's no separate "starting robot" setting apart from these two — whatever gets constructed there is the starting robot.
Description Hand-written prose in question.html, or generated by server.py straight from the test file's own BRIEF_DESCRIPTION and world/expected-state data The generated-prompt pattern (item 5 in the progression below) means the prompt can never go stale relative to what's actually being graded — worth graduating to once a question stabilizes.
Starter code STARTER_CODE — the stub shown to the student, or a class with one method stubbed out (def someMethod(self): pass) for isolated-method questions Just a string, dropped verbatim into question.html.
Which check_* calls matter A short list of function calls in main(), appended to a tests list The one genuinely bespoke part of most test files — see the full menu below.

✓ What takes care of itself — never touch these

Everything inside run_student() and finalize(): resetting the world/robot singleton to a clean state each run, executing the student's file headlessly via runpy, recording the full (robot, action) event log the replay animation is built from, deriving world size from STARTING_WORLD's own streets/avenues lines (parse_world_size()) instead of a separately-hardcoded constant, summing all the check_* points into one score, and writing results.json in the shape PrairieLearn expects. A per-question test file's main() is normally under 20 lines.

Reference: the check_* library

Every condition below is independent and optional — a test file only calls the ones it cares about, in any combination. Full docstrings (exact parameters, edge cases) live in pl_adapter.py itself and in tests/karel/README.md; this is the "which one do I want" menu.

FunctionChecks
check_crashed(result)Did the program crash at all (and where) — call this first and skip the rest of your checks if it did.
check_robot_end_state(result, EXPECTED_ROBOT)Position, direction, and beeper count in one call — the default choice for "did the robot end up right." Returns a list of separate tests, so a student sees exactly which piece (if any) missed.
check_position / check_direction / check_beepersThe three individual pieces check_robot_end_state() calls under the hood — reach for one directly only if you want just that one thing checked.
check_world(world, EXPECTED_WORLD_TEXT)The whole world's beeper layout after the run — not just what the robot itself is carrying.
check_beeper_at(world, street, avenue)One specific corner, instead of the whole world.
check_action_count(robot, N)Total number of primitive actions performed — catches a "technically ends in the right place, but took 40 pointless extra moves" solution.
check_robot_count(result, N)How many robot instances were actually constructed (by ID, from the event log) — catches reassigning the same variable name to a fresh robot already sitting at the goal.
check_class_exists / check_methods_defined / check_method_countOOP shape: the right class exists (optionally extending a given base), and it defines specific methods — or at least N of its own, name unimportant.
check_methods_called(called_methods, [...])Were those methods actually invoked, not just defined — needs run_student_tracking_methods() in place of plain run_student() to populate called_methods.
check_oop_design(result, called_methods, SPEC)One dict bundling all three OOP checks above (exists / defines / called), check_robot_end_state()-style.
check_solving_method_alone(result, class_name, constructor_args, method_name, ...)Constructs a fresh instance and calls just that one method, proving it solves the problem by itself rather than being propped up by extra code in main(). Add required_calls=[...] to also require specific helper methods get called somewhere during it.
check_boolean_method(result, class_name, constructor_args, method_name, expected_return)An isolated boolean "sensor" method, e.g. beeperInFront() — checks both the return value and that the call had no side effects on the robot's position/direction/beepers.
check_path_vs_model(robot, MODEL_SOLUTION_TEXT)Compares the student's actual (street, avenue) path against a model solution's own recorded path, ignoring direction/beepers/turn-count. Defined and ready to use — no built question calls it yet.

Reference: render_world_snapshot()

The one function doing all the actual drawing behind every before/after picture in this course, including the click/pick questions in §08 — worth knowing cold. It renders one static, frozen frame (no animation) of a Karel world, optionally with a robot drawn into it, as a self-contained SVG string — the exact same drawing code the grading replay animation uses (build_svg_animation(), just fed a one-event log instead of a whole run), so a picture can never quietly drift out of sync with what the world text actually says.

# pl_adapter.render_world_snapshot(world_text, robot=None, world_streets=None, world_avenues=None) -> svg_text: str
#
# world_text     (str, required) - .kwld-format world text.
#     world_text = """KarelWorld
#     streets 4
#     avenues 4
#     beepers 2 3 1
#     """
#
# robot          (dict or None, default None) - {"street", "avenue",
#     "direction", "beepers"}; all four required if given. "direction" is
#     a string: "East", "North", "West", or "South". None draws the bare
#     world with no robot in it at all.
#     robot = {"street": 2, "avenue": 3, "direction": "North", "beepers": 1}
#
# world_streets  (int or None, default None) - canvas height, in corners.
#     None derives it from the `streets N` line inside world_text instead.
#     world_streets = 4
#
# world_avenues  (int or None, default None) - canvas width, in corners.
#     None derives it from the `avenues N` line inside world_text instead.
#     world_avenues = 4
#
# Returns: svg_text (str) - a complete, self-contained "<svg>...</svg>"
# string. Hand it straight back from a PrairieLearn file() hook, or embed
# it directly into a chunk of HTML - both are equally valid.

svg_text = pl_adapter.render_world_snapshot(
    world_text="""KarelWorld
streets 4
avenues 4
beepers 2 3 1
""",
    robot={"street": 2, "avenue": 3, "direction": "North", "beepers": 1},
    world_streets=4,
    world_avenues=4,
)

See questions/baker_karel_pick_final_state_simple/server.py for this exact call wired up against real (non-hardcoded) data, with the same documentation reproduced right above the call site.

Example progression — simple to fully automated

All seven of these solve some version of "packy picks up a package, carries it around a wall, drops it off" or a short trace-by-hand program. Read them in this order; each adds exactly one new idea on top of the last.

1 · baker_karel_uicsimplest

Everything hardcoded in karel_tester.py: a fixed starting robot, a fixed expected ending position. Hand-written question.html.

2 · delivery_simple

Adds a real starting/ending world (walls, beepers) as embedded .kwld text, checked with check_world()/check_robot_end_state().

3 · delivery

Same problem, but the world loads from a file on disk, and the expected ending state is derived by actually running a model solution — never hand-typed.

4 · delivery_objects_and_methods

Adds OOP-design checks: does the right class/methods exist, were they actually called (not just defined), does one "solving method" solve the whole problem alone.

5 · same three, + server.pyautomated

The delivery questions' question.html is now a thin Mustache template — server.py reads karel_tester.py live and generates the prose and the before/after pictures on every variant. Edit the test file; the prompt follows automatically, no build step.

6 · click_final_statenew interaction

Not a coding question at all: trace a short program by hand, click the grid, pick the facing. See §08.

7 · pick_final_statenew interaction

Same trace-by-hand idea, multiple-choice instead of click-to-place. See §08.

7b · pick_final_state_simpleread this first

The exact same question as #7, but every fact is a hardcoded constant in one file and the distractors are typed-out dicts instead of a rotation formula — start here if #7's helper functions are hard to trace, then "graduate" to #7 once hardcoding everything feels tedious.

✓ One-paragraph pitch, if you're describing this to someone else

Our Karel test files don't just grade a submission — they report back exactly what the world and robot did, which is enough to render an animated SVG replay for feedback. We took that one step further: the same test file (starting world, expected ending state, OOP requirements) also contains everything needed to generate the question prompt itself — the before/after pictures and the English description of the goal — so a question author writes the grading logic once and gets a correct, never-stale prompt for free.

08 Karel: click/pick questions (the old "open problem")

The previous version of this page flagged Karel's four-direction facing as an unsolved design question between two incompatible prototypes. Resolved: use pl-drawing natively (no custom canvas/JS, no custom parse()/grade()) for position, and a plain pl-multiple-choice for facing — Karel only ever faces exactly one of 4 cardinal directions, so there's no "close enough" angle to reason about, which makes pl-vector's angle-tolerance machinery more trouble than it's worth here.

baker_karel_click_final_state

Shows a short program (pl-code) and the starting world drawn with pl-drawing's own primitives (pl-line/pl-circle/pl-rectangle — not the SVG renderer from §07, since pl-drawing needs objects placed in its own pixel space to grade against). The student clicks "Add point," drags it onto the corner where the robot ends up, and separately picks its facing from 4 radio buttons. No external grading container anywhere — both parts grade natively inside PrairieLearn's own server process.

The correct answer is never hand-typed: server.py actually runs the displayed code through the real karel library headlessly (same trick as a model solution in §07) to get the true final state.

baker_karel_pick_final_state

Same scenario, multiple-choice instead of click-to-place: four rendered "after" pictures (via the same render_world_snapshot() from §07, so these do look like the delivery questions' pictures), one correct and three mechanically-generated distractors — wrong facing, one step short, one step too far. pl-multiple-choice handles shuffling and grading on its own.

⚠ One gotcha that cost real debugging time

pl-drawing color attributes only accept real CSS colors ("gold", "black") or PrairieLearn's own named palette ("gray1", "blue2", …) — not a palette name that doesn't exist, like "gold1" or "white1". Sync doesn't catch this at all; it only throws (ValueError: Attribute "color" must be a CSS-style RGB string) the first time a variant actually tries to render. If a pl-drawing question won't load, check colors first.

Second gotcha: a pl-drawing-button doesn't place a point where you click — clicking it drops a new point at a fixed default corner, which the student then has to drag onto the right spot. Say this explicitly in the question prompt, or students will click uselessly and never find the drag.

Not built yet: sketch the whole path

Asked for but not attempted: instead of just the final corner, have the student click out the entire sequence of corners the robot visits. pl-drawing has no multi-point "path" object, but one native approach should work — give the student N copies of the pl-point button (one per expected corner in the model's real recorded path) and grade each independently via pl-drawing-answer, same mechanism as above just repeated. The real limitation: it only works for a path of a length you already know, so a student who (wrongly) thinks the path is longer or shorter than the model's has nowhere to put the extra/missing clicks. Comparing an arbitrary-length submitted path against the model's actual path (à la kareltestutils.describePathDivergence, already used in §07's check_path_vs_model) would need a custom parse()/grade() in server.py instead of native grading — a bigger lift, not yet prototyped.
